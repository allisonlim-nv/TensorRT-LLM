## 1. Native Behavior

Source: `native_ground_truth.md` (this session, reading `kvCache.cpp`, `kvCacheManager.cpp`, `storageManager.cpp`, `cudaVirtMem.h`, `tokenIdExt.cpp`, and nanobind binding glue at `cpp/tensorrt_llm/nanobind/batch_manager/kvCacheManagerV2.cpp` — none of these `.cpp` bodies had been read in any prior session).

### 1a. `KvCache::resize()` exact semantics

- **No-op vs. real successful resize are indistinguishable via the return value.** Both return `true` — the shortcut path (`kvCache.cpp:1053-1056`, covering genuine no-ops and small in-block changes) and the full/slow path (`kvCache.cpp:1279`, covering real cross-block changes) share the identical `true` return. **Verified current behavior** (`kvCache.cpp:1022-1056,1279,1301-1345`).
- **Omitting `historyLength` leaves the field semantically unchanged** (`newHist = historyLength.value_or(mHistoryLength)`, `kvCache.cpp:1028`) but skips updating the `mAvgHistoryLength` moving-average side-channel (`kvCache.cpp:1032`), which *would* be touched if the caller passed the current value explicitly instead of omitting it — a real, minor side-effect asymmetry. **Verified current behavior** (`kvCache.cpp:1028-1033`).
- **Failure (`return false`) is atomic-by-explicit-rollback, but only for `OutOfPagesError`.** The sole `false` return (`kvCache.cpp:1143`) is reached only inside the growing/no-shrink branch when `newGpuSlots(...)` throws `OutOfPagesError`; the catch block (`kvCache.cpp:1139-1144`) calls `_recoverExcessScratchSlots`/`_lockHeldBlocks` to restore pre-call state, and `mCapacity`/`mHistoryLength` are only committed after allocation succeeds (`kvCache.cpp:1274-1275`), so nothing is mutated before a possible `OutOfPagesError`. **Verified current behavior** (`kvCache.cpp:1067-1144,1274-1279`).
- **Every other exception type (`CuError`, `std::invalid_argument`, assertion failures) propagates uncaught, without rollback.** `kvCache.cpp:1036,1038` throw `std::invalid_argument` for invalid history-length arguments (checked before any mutation, so these are safe); a debug-only `TLLM_CHECK_WITH_INFO` (`kvCache.cpp:1042-1047`) can throw a `TllmException`; and any non-`OutOfPagesError` exception from `newGpuSlots(...)` (e.g. `CuOOMError`/`CuError` from an underlying CUDA driver failure) is **not** caught by the `catch (OutOfPagesError const&)` block and escapes `resize()` uncaught, with no rollback run in that case. This is a real asymmetry: the `false`-return path is safely rolled back; an uncaught-exception path is not proven safe. **Verified current behavior for the asymmetry existing; source-inconclusive whether an uncaught CUDA-error path during a real (non-two-manager-related) resize is ever actually reachable in practice**, since it depends on whether the underlying CUDA allocator can fail with something other than out-of-memory during a page grab — **Source-inconclusive, requiring native/runtime test** (would need to force a non-OOM CUDA failure mid-resize and observe the resulting `_KVCache` state).
- **Tier-level `KvCacheManager::resize(CacheLevel, quota, bestEffort)`** converts *any* `std::exception` to `false` (swallowing the specific type) via a blanket `catch (std::exception const& e)` (`kvCacheManager.cpp:420-433`); `bestEfforts=true` is unconditionally unimplemented (throws immediately). Whether a failed `_adjustLevel(level, quota)` call leaves `StorageManager` partially adjusted was **not traced** (its body was out of scope for this pass). **Source-inconclusive, requiring native/runtime test** (`kvCacheManager.cpp:420-433`, open question in native_ground_truth.md item 1).

### 1b. Process-terminating vs. Python-catchable exceptions

- **`terminateOnException` has exactly one call site in the entire codebase**, guarding only `StagingBufferManager::~StagingBufferManager()` (`stagingBuffer.cpp:157-169`) — unrelated to any `KvCache`/`KvCacheManager` public method. No `resize`, `suspend`, `createKvCache`, `resume`, or `commit` call is wrapped by it. **Verified current behavior** (repo-wide grep confirmed, `native_ground_truth.md` Task 2.1).
- **nanobind's default behavior is "propagate as a catchable Python exception," not "abort."** The binding module explicitly registers Python exception classes/translators for the entire `kv_cache_manager_v2` exception hierarchy (`OutOfMemoryError`, `HostOOMError`, `DiskOOMError`, `CuOOMError`, `LogicError`, `ResourceBusyError`, `OutOfPagesError`, `CuError`, and an `AssertionError` mapping) at `kvCacheManagerV2.cpp:787-849`. **Verified current behavior.**
- **`KvCache::suspend()` and `KvCacheManager::createKvCache(...)` are plain `.def` bindings with no manual try/catch and no `terminateOnException` wrapper** (`kvCacheManagerV2.cpp:1686`, `:2216-2230`). Neither is declared `noexcept` in the headers. Therefore a `CuError`/`AssertionError`/`LogicError` raised inside either call propagates to Python as a catchable exception, **not a process abort**, for the direct call paths read. **Verified current behavior.** This directly closes the JIRA audit's Open Question about whether `_suspend_request`'s sequential primary-then-draft `suspend_request` calls could abort the process on failure — they do **not** abort the process; a failure there raises a normal, catchable Python exception (though, per the JIRA audit, `_suspend_request` itself has no `try/except` around the two sequential calls, so an exception there still propagates uncaught up through the scheduler — that scheduler-side gap is unchanged by this finding, only the "does it abort the process" sub-question is now closed).
- **Narrow residual gap:** whether any transitive callee of `suspend()`/`createKvCache()` ever synchronously destructs a `StagingBufferManager` with a live buffer (which *would* route through the one `terminateOnException` site and abort) was not exhaustively traced across the full call graph. **Source-inconclusive, requiring native/runtime test** (though assessed as unlikely under normal operation per `native_ground_truth.md` Task 2.3).

### 1c. Target/draft native object independence

- **Fully independent GPU memory pools, CUDA virtual-memory allocators, event sinks, and CUDA streams.** Each `KvCacheManager` instance constructs its own `mRadixTree` (`kvCacheManager.cpp:116`) and its own `mStorage`/`StorageManager` (`:119-121`), which in turn owns its own `unique_ptr<PooledPhysMemAllocator>` (`storageManager.cpp:283-285`) with no static/global pool inside it (`cudaVirtMem.h:55-93`, copy-construction explicitly deleted). `eventSink` defaults to `nullptr` (no shared/global fallback) at both the C++ constructor (`kvCacheManager.h:107`, `kvCacheManager.cpp:109`) and the Python binding layer (`kvCacheManagerV2.cpp:2168-2209`). **Verified current behavior.**
- **One confirmed process-global singleton exists: `DigestPool::instance()`** (`tokenIdExt.cpp:33-56`, Meyers singleton, mutex-guarded), used by every `TokenIdExt` instance across the whole process — including target and draft managers both — for multi-modal digest hashing. This is deliberate, documented (`tokenIdExt.cpp:36-46`, "a single static singleton is safe"), and mutex-protected, so not a data race, but it **is** genuine shared mutable state that a bug in one manager's digest bookkeeping could in principle affect the other manager through, when multi-modal inputs are in play. **Verified current behavior.**
- **Conclusion:** target and draft native manager instances are independent for every resource examined **except** the one documented `DigestPool` singleton (multi-modal digest hashing only). **Verified current behavior**, with the caveat that a full transitive audit of every static/global was not exhaustively performed beyond the patterns grepped (`native_ground_truth.md` states the grep methodology explicitly).

## 2. Scheduler/Executor Ordering

Source: `executor_ordering.md` (this session, tracing `py_executor.py`'s three iteration loops and `resource_manager.py`'s dispatch registry — none of this had been traced beyond call-site inventory in any prior session).

### 2a. Do target scheduler admission and draft-manager resource prep see the same request set in the same iteration?

- **Yes, for the primary case: no cross-iteration skew.** `resource_manager.prepare_resources(scheduled_batch)` (`py_executor.py:4261` non-overlap, `:5094` overlap, `:2715` PP) always operates on the **current** iteration's `scheduled_batch`, built fresh from `scheduler.schedule_request`'s return value within the same synchronous call (`_schedule()`, `py_executor.py:6271-6333`, calling `schedule_request` at `:6276`). There is no deferred/queued version of this dispatch. **Verified current behavior.**
- **But within one iteration, the scheduler's true admission decision can be a superset of what `prepare_resources` (and thus draft mirroring) actually sees.** Two filters inside `_schedule()` can drop context requests from `scheduled_batch.context_requests` **without** calling `revert_allocate_context` — `_waiting_requests` (`py_executor.py:6064-6082`, batch-waiting threshold) and `_cap_context_by_total_kv_len` (`py_executor.py:6249-6268`, fp8-context-MLA cap) — both documented in-code as accepted trade-offs ("Requests dropped for batch waiting still occupy KV cache," `py_executor.py:6303-6304`). This means the draft manager never even attempts to mirror these requests until a later iteration when the scheduler re-admits them — a subtraction-only skew, not a different/reordered request set. **Verified current behavior.** (Contrast: the disagg-specific `_apply_disagg_transfer_admission` deferral path **does** properly call `_revert_ctx_alloc` before proceeding — `py_executor.py:3566-3568,3587-3588` — so that specific deferral path is not subject to this gap.)

### 2b. Registry composition and ordering

- `ResourceManager.prepare_resources`/`update_resources` iterate an `OrderedDict` unconditionally with no per-`ResourceManagerType` filtering (`resource_manager.py:3001-3037`); `reorder_pipeline` exists but has **zero callers** on this commit (confirmed by repo-wide grep) — registration order (target inserted before draft before cross, `_util.py:2104-2108`) is the effective, always-synchronous iteration order. When `draft_kv_cache_manager is None`, the dict slot is skipped via a plain `hasattr(None, "prepare_resources") == False` check, not special-casing. **Verified current behavior.**

### 2c. Rollback scope — does reverting target capacity also revert draft's mirrored growth?

- **No — confirmed by exhaustive grep, and this has a real (not merely theoretical) trigger window.** All four `revert_allocate_generation`/`revert_allocate_context` call sites in `py_executor.py` (`:3438,3477,4217,5048`) target `self.kv_cache_manager` only; none ever calls `self.draft_kv_cache_manager.revert_allocate_*`. **Verified current behavior.**
- **The concrete trigger:** in `_executor_loop` (`py_executor.py:4248-4275`) and `_executor_loop_overlap` (`:5067-5109`) — but **not** `_executor_loop_pp` — whenever a KV connector is configured (`self.kv_connector_manager`, assigned unconditionally from a constructor argument at `py_executor.py:985` whenever one is configured; not a test-only path), there are **two** sequential `can_queue` votes with `resource_manager.prepare_resources(scheduled_batch)` sandwiched between them. If the *first* vote is `True`, `prepare_resources` runs — including the draft manager's real, capacity-mutating `_prepare_draft_resources` mirroring (`kv_cache_manager_v2.py:2779`) — and only *then* does the second, kv-connector-triggered `can_queue` re-check run; if it flips to `False`, `_revert_gen_alloc` fires but reverts **only** `self.kv_cache_manager`'s growth for the same request set. The draft manager's already-mirrored growth for those exact requests is never rolled back in this code path. **Verified current behavior** (`py_executor.py:4248-4275,5067-5109`, exact structure quoted in `executor_ordering.md` §3).
- **`_executor_loop_pp` is structurally immune to this specific race**: its single `can_queue` check (`py_executor.py:2682`) and matching revert (`:2690`) both occur strictly *before* `prepare_resources` (`:2715`) — there is no second re-check afterward. **Unreachable on this commit**, for the PP loop specifically.
- **Whether the un-reverted draft-manager mirror in the non-PP/overlap case constitutes an actual resource leak, or self-heals** (e.g., because `_prepare_draft_resources` recomputes the draft's capacity idempotently from `req.context_current_position`/`req.context_chunk_size` on the next iteration the same still-active request is scheduled, rather than incrementally accumulating) **was not determined** — this requires reading `KVCacheManagerV2._prepare_draft_resources`'s grow/shrink call graph in the depth this pass did not cover (it was scoped to executor ordering, not manager internals). **Source-inconclusive, requiring unit/fault-injection test** — specifically, a test that forces the kv-connector's second `can_queue` vote to flip after `prepare_resources` has run, then inspects the draft manager's page/capacity counters before and after `_revert_gen_alloc`, across at least two consecutive iterations to check for compounding drift (`executor_ordering.md` §3, Open Questions 1-2).

### 2d. Forward-pass ordering

- In all three loops, the forward pass (`self._forward_step(...)`) is placed strictly after `resource_manager.prepare_resources(scheduled_batch)` for that same iteration's `scheduled_batch`, gated on the final (post-second-check, where applicable) value of `can_queue`. The draft model's own forward pass (`self.drafter.prepare_draft_tokens`/`self._handle_speculative_decoding`) likewise occurs strictly after `prepare_resources`, within the same `if can_queue:` block. There is no interleaving window where the draft model's forward pass could start before its own KV manager's `prepare_resources` has run for the current iteration. **Verified current behavior** (`py_executor.py:4261,4297,4332` non-overlap; `:5094,5153,5185` overlap; `:2715` PP, structurally).

### 2e. Overlap-executor multi-iteration skew

- **`prepare_resources` (capacity growth/mirroring) is NOT skewed** — always same-iteration as `schedule_request`, confirmed directly. **Verified current behavior.**
- **`update_resources` (post-forward bookkeeping, incl. capacity release) IS intentionally skewed by exactly one iteration** in the overlap loop, operating on `self.previous_batch.scheduled_requests` (`py_executor.py:5414-5428`, captured at `:5300-5309`) — but this skew is applied **uniformly** across all registered manager types via the same registry dispatch and the same `scheduled_requests` argument, so there is no *additional* skew between target and draft specifically within `update_resources`. **Verified current behavior.**
- `GENERATION_TO_COMPLETE` is confirmed **unrelated** to KV capacity or draft mirroring — it only gates logits-exclusion bookkeeping (`py_executor.py:7765-7807`); grep confirms no reference to it in `resource_manager.py` relevant to KV-cache resource preparation. **Verified current behavior** — this directly resolves the earlier coverage-closure open item about whether `GENERATION_TO_COMPLETE` has an analogous KV-layer carve-out: it is orthogonal, not analogous.
- **Whether the §2c un-reverted-mirror gap combined with the one-iteration-skewed `update_resources` release could compound into multi-iteration drift under sustained kv-connector `can_queue` flips** was not determined by static reading. **Source-inconclusive, requiring unit/fault-injection test** (`executor_ordering.md` §5, residual point).

### 3b. Prefix-reuse correctness for target vs. draft

- **Draft manager never consults reuse — verified mechanism, at the Python level.** `_prepare_draft_resources` unconditionally passes `input_tokens=None` to `_create_kv_cache` (`kv_cache_manager_v2.py:2789-2797`), regardless of `self.enable_block_reuse` — so the draft's `_KVCache` never attempts a `matchReuse`/prefix-match call; `num_committed_tokens=0` for the draft at creation. This is consistent with the separately-known fact that `try_commit_blocks` also explicitly excludes draft managers from *committing* reusable blocks (`kv_cache_manager_v2.py:3651-3656`) — the draft's radix tree is functionally inert on both the read and write side. **Verified current behavior.**
- **The draft's chunk bookkeeping is seeded from (two-model) or literally identical to (one-model) the target's reuse-shortened position**, meaning the draft's own forward computation is told to skip exactly the range its own cache never populated by any mechanism. This mechanical fact (target reuses tokens `[0,800)`, draft's cache has `num_committed_tokens=0` for that same range, and draft's chunk bounds are `[800,1000)` too) is **Verified current behavior**, traced concretely through `model_engine.py:5401-5411`, `py_executor.py:7788-7792`, `model_drafter.py:140-149`.
- **Whether this produces actual data corruption (garbage KV reads) is unresolved.** Two candidate outcomes were identified: (a) the draft's attention kernel reads uninitialized GPU memory for the un-populated range (a correctness bug, possibly bounded by the target's own accept/reject step), or (b) some native mechanism gates the draft's effective attention span to its own `_KVCache.history_length` (which, per §1a above, is left at its prior value — `0` for a freshly-created draft cache, since `_prepare_draft_resources`'s `kv_cache.resize(capacity)` call omits the `historyLength` argument, `kv_cache_manager_v2.py:2810-2821`) rather than trusting `req.context_current_position`. Distinguishing these requires reading the draft's attention-metadata construction path (`speculative/interface.py`, not read in either session) to see whether it consumes `history_length` or `context_current_position`/`py_last_context_chunk` when building the KV span fed to the attention kernel. **Source-inconclusive, requiring native/runtime test** (this closes part of, but not all of, the prior session's Open Question — §1a of this document now confirms `history_length` genuinely stays at its prior/unset value when the argument is omitted, which sharpens outcome (b) as plausible, but does not confirm which outcome actually occurs without reading the attention-metadata consumer).
- **The folded/shared-manager topology (Mode C) is structurally immune to this entire mechanism.** With one `_KVCache` per request, reuse is resolved once and applies atomically to all layer groups — there is no second, independently-reuse-resolved cache to diverge. **Verified current behavior** (there is nothing to diverge from, by construction — `_prepare_draft_resources` is not even reachable in this topology since no separate draft `KVCacheManagerV2` exists).
- **Is the reported scenario reachable on this commit?** For Modes A/B (separate-manager topologies): **the mechanism is Verified current behavior as a reachable code path** (no guard disables block reuse when a separate draft manager is configured — confirmed by grep across `_util.py`, `llm_args.py`, `speculative/*.py`). Whether it manifests as an actual observable correctness defect (vs. being masked by a native gating mechanism) remains **Source-inconclusive, requiring native/runtime test**. For Mode C: **Unreachable on this commit.**

## Smallest Ordered Set of Remaining Tests Before a Refactor Design Can Be Safely Proposed

Ordered by how directly each item gates a load-bearing claim the refactor's motivation would otherwise rest on:

1. **[Native/runtime test — highest priority]** Read (or, if source-exhausted, instrument) the draft engine's attention-metadata construction path (`tensorrt_llm/_torch/speculative/interface.py`, not read in any session) to determine whether it consumes the draft `_KVCache`'s own `history_length` (safe-but-degraded) or `req.context_current_position`/`py_last_context_chunk` copied from the target (potentially unsafe) when building the KV span for the draft's attention kernel. This is the single highest-value open item: it converts §3b's "mechanism is reachable" finding into either "confirmed correctness defect, migrate/fix with urgency" or "safely gated, motivation is architectural simplification only, not correctness."
