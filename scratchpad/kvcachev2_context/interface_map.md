## 2. Target/Draft Lifecycle Alignment

**Aggregate (non-disagg) speculative decoding:**
- Scheduler's `req_tokens = beam_width + get_draft_token_length(req)` (`scheduler_v2.py:984`) vs. manager's `_effective_draft_len(req)` used inside `try_allocate_generation`/`_required_gen_capacity` (`kv_cache_manager_v2.py:2410-2429,2458-2463`).
- **Re-verified directly:** `_effective_draft_len` returns `get_draft_token_length(req)` unmodified **unless** `draft_len == 0 and req.is_disagg_generation_transmission_complete and req.context_phase_params is not None` (`kv_cache_manager_v2.py:2418-2429`). In the ordinary aggregate (non-disagg) path this guard is never true, so **the two draft-length computations are numerically identical for aggregate speculative decoding.** This resolves scheduler.md's Open Question 8 for the aggregate case: no divergence.
- The scheduler never calls capacity-affecting methods on `draft_kv_cache_manager` — only `suspend_request`/`free_resources` mirrors (manager.md §7 confirms `prepare_resources`/`_prepare_draft_resources` self-drives the draft manager's per-request lifecycle from the executor, once per iteration, independent of the scheduler's target-manager calls).
- **Verified fact (source of truth):** `_prepare_draft_resources` pads generation-request resize to `_kv_reserve_draft_tokens` beyond `_required_gen_capacity`, and `update_resources` reclaims unused dynamic-tree reserve slack for draft managers only (manager.md §7, §12.5 test corroboration with concrete numbers: 201 vs. 230 capacity). This is manager-internal accounting the scheduler never queries or budgets against — the scheduler's `BudgetTracker` token math and the manager's KV-page reservation for draft capacity are **two independently-sized quantities that happen to agree only because the manager reserves *at least* what the scheduler's `get_draft_token_length` implies**, plus manager-side slack.

**Disaggregated path (context→generation transition):**
- **Confirmed divergence exists, scoped narrowly.** When `draft_len == 0` and the request is mid disagg-generation-transmission-complete transition, `_effective_draft_len` substitutes either the transferred `context_phase_params.draft_tokens` length or, if that's also empty, `self.max_total_draft_tokens` (the generation worker's configured draft capacity) (`kv_cache_manager_v2.py:2419-2428`). During this exact window, `try_allocate_generation`'s manager-side KV-page reservation can exceed what the scheduler's own `get_draft_token_length(req)`-based `BudgetTracker.commit` accounted for, because `req.py_draft_tokens` is still empty at scheduling time in this transition.
- This is a **confirmed mismatch** in the strict sense that both sides' code is directly cited and the discrepancy is concrete (see §5 below) — but its blast radius is the disagg-gen-init→first-decode transition specifically, not steady-state aggregate spec decoding.
- The disagg-specific draft/spec resource lifecycle (`prepare_resources` over `(KV_CACHE_MANAGER, SPEC_RESOURCE_MANAGER, DRAFT_KV_CACHE_MANAGER)` for `fitting_disagg_gen_init_requests`) is driven entirely by `py_executor.py:_prepare_disagg_gen_init`, not the scheduler (scheduler.md §11) — consistent with manager.md's finding that the scheduler only ever touches the primary manager directly.

## 4. Scheduler `BudgetTracker` vs. Manager/Native Page Accounting

- **These are two structurally independent accounting systems with no reconciliation API between them**, confirmed by both reports:
  - `BudgetTracker` (scheduler_v2.py:51-141) tracks `num_tokens`/`num_requests`/PEFT pages **in Python, per scheduling iteration only** — it has no notion of KV pages, tiers, or native capacity at all. It is reset fresh every `_schedule_loop` call (scheduler.md §2).
  - The manager's capacity accounting (`get_kv_cache_stats()`, `get_iteration_stats()`) is **GPU-tier-only** for `get_kv_cache_stats()` (manager.md §10, §11.7) — no host/disk occupancy surfaces through that struct. `get_iteration_stats()` does expose `suspended_requests`/`resumed_requests` **counts** but was not confirmed (by either report) to expose host/disk **byte/block** occupancy (manager.md §9b, Open Q10).
  - The scheduler never calls either stats method as part of its scheduling decisions (no citation in scheduler.md references `get_kv_cache_stats`/`get_iteration_stats` from `scheduler_v2.py`) — scheduling decisions are made purely via the try/fail pattern (`try_allocate_generation`, `resize_context`, etc. returning bool), not by querying available capacity up front. This matches `can_schedule`'s own docstring: "V2's try-and-see model lacks a free-blocks query API" (scheduler.md §10, `scheduler_v2.py:1250-1259`).
- **PEFT vs. KV-page "not yet released" transient state (scheduler.md Open Q10):** `pre_claim_peft` reserves *PEFT-cache* budget for `GENERATION_TO_COMPLETE` requests whose adapters aren't yet released. **Re-verified via grep:** `kv_cache_manager_v2.py` contains **zero references to `GENERATION_TO_COMPLETE`/`is_generation_to_complete`** — the manager has no analogous "not yet released" KV-page carve-out for this state. This means the scheduler's KV-page-affecting calls (`try_allocate_generation`, `is_request_active`) do **not** need (and do not have) an equivalent pre-claim mechanism for `GENERATION_TO_COMPLETE` requests at the KV layer — consistent with `update_resources`'s documented completion short-circuit (`new_capacity = None` for `GENERATION_COMPLETE`/`CONTEXT_INIT`, manager.md §9 `update_resources`), which sidesteps the issue by simply not resizing capacity for those states rather than needing a pre-claim.
- **No drift risk was found between the two systems for token/request bookkeeping**, because they measure entirely different resources (Python-side scheduling-slot/token counters vs. native KV pages) and the scheduler's admission decisions are gated by the manager's try/fail return values, not by the scheduler independently predicting manager capacity. The systems are decoupled by construction, not reconciled — there is no single source of truth for "how much KV capacity is left," only per-call success/failure signals.

## 5. GPU / Explicit Host-Disk / Auto-Host Provisioning Semantics

- **Verified fact (manager.md §6.2):** auto host-tier provisioning exists specifically because "the V2 MAX_UTILIZATION scheduler relies on suspend/resume to evict and later restore KV cache pages. Without a secondary tier, suspended held pages cannot migrate out of GPU, so suspension cannot free capacity and scheduling can deadlock." This is a **direct, load-bearing dependency of scheduler correctness on manager-side tier provisioning** — the scheduler's `_try_evict_for_gen`/deadlock-avoidance logic implicitly assumes *some* secondary tier normally exists (auto-sized to at least the GPU quota) unless the operator explicitly set `host_cache_size=0`.
- **Confirmed mismatch-risk (fleet-wide silent degradation):** if any single rank's host-tier construction fails (`CuError`/`KVCacheOutOfMemoryError`), **all ranks** fall back to `USE_NO_HOST` and lose the host tier fleet-wide, setting `can_evict = False` everywhere (manager.md §6.4, §11.10). The scheduler has **no code path that detects or logs this transition** — `can_evict` is read as a static attribute (§1 table row) with no scheduler-side awareness that it could differ from what was configured at startup. This is a genuine cross-report-supported risk: scheduler.md documents the scheduler's blind trust in `can_evict`'s truth value; manager.md documents the exact runtime condition under which that value silently becomes `False` for reasons invisible to the scheduler (a construction-time rank failure, not a scheduling-time signal). **Placed in Confirmed Mismatches/Risks below** since both sides are directly cited and the contradiction (scheduler assumes stable `can_evict`; manager can silently flip it fleet-wide at construction with no scheduler-visible signal) is concrete — though note this is a construction-time, not steady-state, degradation.
- **Disk tier:** purely explicit opt-in, no auto-sizing (manager.md §6.3). The scheduler has no distinct code path for "disk tier present vs. absent" — it only ever sees the aggregate `can_evict` boolean, so from the scheduler's point of view, host-only, disk-only, and host+disk configurations are indistinguishable. No mismatch found here — this is a deliberate abstraction boundary, not a gap.
- **`get_kv_cache_stats()` GPU-only scope** (manager.md §10, §11.7, Open Q1): if any external monitoring or scheduler-adjacent logic were to assume this reports host/disk occupancy, it would be wrong — but **no scheduler.md citation shows `scheduler_v2.py` calling this method at all**, so no confirmed scheduler-side reliance on it exists. Listed as unresolved only insofar as `py_executor.py`'s broader use of these stats (outside scheduler scope) was not traced by either report.

## Confirmed Mismatches / Risks

Only items where both reports (or direct re-reading) concretely support a contradiction:

1. **Scheduler reaches into manager private internals for cross-KV (`_try_schedule_cross_context_v2`).** Re-verified directly: `scheduler_v2.py:928-963` calls `cross_kv_cache_manager.kv_cache_map`, `._create_kv_cache(...)`, `._resume_and_restore(...)`, and per-`_KVCache` private-pattern methods (`.resize`, `.suspend`, `.stop_committing`, `.cuda_stream`) instead of the public `prepare_context`/`resize_context` API that every other scheduler call site uses (scheduler.md §6; manager.md §9 `_create_kv_cache`, which documents its public callers as `prepare_context`/`prepare_disagg_gen_init`/`add_dummy_requests`/`_prepare_draft_resources` — **not** the scheduler). This is a structural API-layering violation, not merely under-specified: the scheduler is coupled to manager-internal implementation details (`kv_cache_map`, leading-underscore methods) that no manager docstring designates as a scheduler-facing contract.

2. **`revert_allocate_context` can silently escalate to a full `free_resources` teardown.** Confirmed in manager.md §9: if `kv_cache.history_length > pre_cap` at revert time, the manager calls `self.free_resources(req)` instead of a simple resize-back. Scheduler.md documents the scheduler/orchestration-caller's mental model of this call as "undo the growth" (a `resize`), with no scheduler-side code anticipating a full teardown. Since `free_resources` also releases the IndexMapper slot and native cache, a caller expecting a partial revert gets a full deallocation instead when committed history has already advanced — a concrete, directly-cited behavioral divergence from the naive "revert = shrink" expectation baked into the scheduler-adjacent rollback call sites (`py_executor.py:3477`, per scheduler.md §5a/§4).

3. **Fleet-wide `can_evict` degradation is invisible to the scheduler.** Manager.md §6.4/§11.10 confirms one rank's host-tier construction failure silently disables `can_evict` on **all** ranks. Scheduler.md confirms the scheduler treats `kv_cache_manager.can_evict` as a static, trustworthy attribute with no re-validation or logging of changes (§8c, Open Q6). The contradiction is concrete: the manager's own construction-time rationale (§6.2) states the scheduler's deadlock-avoidance *depends on* a secondary tier existing, yet the manager can silently remove that tier fleet-wide with zero scheduler-visible signal beyond `can_evict` simply reading `False` from then on (which the scheduler cannot distinguish from "no host tier was ever configured").

4. **Draft-length accounting diverges from the scheduler's `BudgetTracker` during the disagg context→generation transition window.** Re-verified directly (`kv_cache_manager_v2.py:2418-2429`): when `req.py_draft_tokens` is empty and the request is mid disagg-generation-transmission-complete transition, `try_allocate_generation`'s manager-side reservation can be `context_phase_params.draft_tokens` length or `self.max_total_draft_tokens`, while the scheduler's `BudgetTracker.commit` for that same request used `get_draft_token_length(req)` (which is `0` in this exact window, since `py_draft_tokens` is empty). This is a concrete, code-level-cited discrepancy, scoped specifically to the disagg-gen transition (not steady-state aggregate spec decoding, where the two are proven identical — see §2).

## Unresolved / Needs Runtime or Native Evidence

1. **`resize_context` failure on non-first chunks** — does the manager suspend the cache on failure the same way it does for first chunks? Docstring/code coverage in both reports is silent for the non-first-chunk case (§3 table).
2. **`context_remaining_length` stability within `_try_schedule_context_chunked`** — no manager-side contract found (positive or negative) guaranteeing no other actor mutates this between `prepare_context` and `resize_context` within one scheduler call (§1 table, scheduler.md Open Q3).
3. **Native `KvCache::resize()` idempotency on repeated failed calls** — the C++ doc comment's "returns true if the resize was a no-op shortcut" phrasing is ambiguous about the non-no-op success case, and `kvCache.cpp`/`kvCacheManager.cpp` were not read by either report (manager.md §9b Open Q6).
4. **`terminateOnException` call sites** — unclear which manager/KvCache methods can call `std::terminate()` (process abort) vs. propagate a catchable Python exception; materially affects what failure handling the scheduler can actually rely on for OOM-class conditions (manager.md §5, §9b Open Q7).
5. **`get_iteration_stats()` field-level coverage of host/disk occupancy** — confirmed to expose suspend/resume *counts*, not confirmed (or denied) to expose host/disk *byte/block* occupancy; `KVCacheV2PoolGroupIterationStats` fields were not catalogued (manager.md §9b, Open Q10).
6. **Per-pool-group resume-rejection threshold semantics** (`max_util_for_resume`) — whether ANY over-threshold pool group blocks a whole-request resume, or only pool groups touched by that request; test name found (`test_resume_rejects_if_any_pool_group_exceeds_threshold`) but body not read by either report (manager.md §12.4, Open Q11).
7. **`add_dummy_requests` callers** — not found in `scheduler_v2.py`/`py_executor.py` grep by manager.md; likely CUDA-graph warmup code elsewhere, not traced by either report (manager.md Open Q5).
8. **Deadlock-detection false positives** (`scheduler_v2.py:456-483` `RuntimeError`) — whether any transient manager-side state (mid-resume, async operation in flight) could look like a true deadlock to the scheduler; not resolvable from either report alone (scheduler.md Open Q9).
9. **`free_resources`'s unused `pin_on_release` parameter** — confirmed dead in the current method body by manager.md (two independent passes); whether any scheduler/orchestration call site passes `pin_on_release=True` expecting an effect was flagged by manager.md as not checked (manager.md Open Q2) — scheduler.md's call-site inventory (`scheduler_v2.py:1100-1102`) does not show this kwarg being passed, but a full grep across `py_executor.py` for this specific kwarg was not performed by either report.
10. **Per-request `GENERATION_TO_COMPLETE` KV-layer transient accounting** — resolved partially: manager has no `GENERATION_TO_COMPLETE`-specific code path (verified via grep, §4 above), but whether this absence is intentional-and-safe (because `update_resources`'s completion short-circuit already handles it) or a genuine unhandled gap for some code path neither report traced (e.g., interaction with `try_allocate_generation` called on a `GENERATION_TO_COMPLETE` request that is *also* still schedulable) remains open.
